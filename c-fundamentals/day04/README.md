# Day 04: 구조체 정렬(alignment)과 패딩

## 목표
1. 구조체 멤버가 어느 offset에 놓이는지 확인 (`offsetof`)
2. 멤버 사이의 패딩과 구조체 끝의 패딩 확인
3. 멤버 순서에 따른 구조체 크기 비교
4. `packed` 구조체의 동작과 위험 이해

## 환경
- 보드: Jetson Xavier NX (ARM64, Ubuntu 20.04, gcc 9.4.0)
- 컴파일: `gcc -Wall -O0 -g align.c -o align`

## 핵심 개념
- **정렬 규칙**: 타입마다 놓일 수 있는 주소가 정해져 있다. `int`(4바이트)는 4의 배수, `double`(8바이트)은 8의 배수, `char`는 어디든 가능.
- **패딩**: 정렬 규칙을 지키려고 컴파일러가 끼워 넣는 빈 공간.
- **비유 (주차장)**: 경차(`char`)는 아무 칸에나 댈 수 있지만, 버스(`double`)는 8칸 단위 전용 칸에만 댈 수 있다. 버스 칸이 시작될 때까지 비워 둔 칸이 패딩이다.
- **왜 필요한가**: CPU는 메모리를 정해진 단위로 읽는다. 값이 단위 경계에 걸치면 두 번 읽어야 해서 느려지거나, CPU에 따라 오류가 난다.

## 실험 코드
```c
struct A { char c; int i; char d; };
struct B { int i; char c; char d; };
struct C { char c; double x; int i; };
struct D { double x; int i; char c; };
struct __attribute__((packed)) P { char c; int i; char d; };
```

## 실행 결과
```
A: size=12, c=0, i=4, d=8
B: size=8, i=0, c=4, d=5
C: size=24, c=0, x=8, i=16
D: size=16, x=0, i=8, c=12
P: size=6, c=0, i=1, d=5
A 배열: &arr[0]=0xfffff5c10ee0, &arr[1]=0xfffff5c10eec
```

## 메모리 배치
```
A: [c][패딩 3][i i i i][d][패딩 3]                  = 12
B: [i i i i][c][d][패딩 2]                          = 8
C: [c][패딩 7][x x x x x x x x][i i i i][패딩 4]    = 24
D: [x x x x x x x x][i i i i][c][패딩 3]            = 16
P: [c][i i i i][d]                                  = 6  (패딩 없음, i가 offset 1)
```

## 분석

### 1. 끝 패딩: 구조체 크기는 가장 큰 멤버 정렬의 배수
- `&arr[1] - &arr[0]` = 0xc = **12바이트**. 멤버 합은 9바이트인데 `d` 뒤에 3바이트 패딩이 있다.
- 이유는 **배열**이다. 크기가 9라면 `arr[1].i`의 주소가 9 + 4 = 13번이 되어 4의 배수가 아니다.
  ```
  arr[0]: 0~8바이트   → arr[0].i는 4번  (4의 배수 ✅)
  arr[1]: 9~17바이트  → arr[1].i는 13번 (4의 배수 ❌)
  ```
- 그래서 구조체 전체 크기를 **가장 큰 멤버의 정렬 단위의 배수**로 맞춘다.
  - A, B: 가장 큰 정렬이 `int`(4) → 4의 배수 (12, 8)
  - C, D: 가장 큰 정렬이 `double`(8) → 8의 배수 (24, 16)

### 2. 멤버 순서가 크기를 바꾼다
| 같은 멤버 | 순서 | 크기 |
|---|---|---|
| char 2개, int 1개 | A: char int char | 12 |
| | B: int char char | **8** |
| char, double, int | C: char double int | 24 |
| | D: double int char | **16** |

- **큰 멤버부터 작은 멤버 순서로 선언하면 패딩이 줄어든다.**
- 컴파일러는 멤버 순서를 **바꾸지 않는다.** C 표준이 선언 순서를 유지하도록 정해 두었기 때문에, 순서를 바꾸는 것은 프로그래머의 일이다.

### 3. packed 구조체
- 패딩이 없어 6바이트지만, `i`가 offset 1처럼 4의 배수가 아닌 곳에 놓인다.
- **쓰는 곳**: CAN 메시지, 네트워크 패킷 헤더, 파일 형식처럼 바이트 배치가 정확히 정해진 경우.
- **위험**:
  - 정렬되지 않은 접근은 느려질 수 있다. ARM64 리눅스의 일반 변수는 대부분 동작하지만, 원자 연산, 장치 메모리, 작은 MCU(Cortex-M0 등)에서는 fault가 날 수 있다.
  - packed 멤버의 주소를 일반 포인터(`int *p = &pkt.i;`)로 꺼내면, 그 포인터는 정렬된 것으로 가정하고 동작해서 위험하다. gcc도 경고를 낸다.
- **실무 방식**: 수신한 바이트를 packed 구조체로 해석한 뒤, 일반 구조체로 복사해서 사용한다.

### 4. 실무에서 왜 중요한가
- 구조체 하나에서 8바이트를 아끼면, 텐서 메타데이터 100만 개를 다룰 때 8MB를 아낀다.
- 드라이버 레지스터 맵, CAN 메시지처럼 바이트 위치가 정확해야 하는 곳에서 패딩을 모르면 버그가 생긴다.
- 프로젝트 A의 메모리 플래너에서 버퍼 offset을 정할 때도 같은 정렬 규칙을 적용해야 한다.

## 연습 문제: struct E
```c
struct E { char a; double b; char c; int d; };
```
```
원래: [a][패딩 7][b × 8][c][패딩 3][d × 4]   = 24
수정: [b × 8][d × 4][a][c][패딩 2]           = 16   (double int char char)
```
- 24 → 16바이트로 33% 감소
- 패딩 계산 팁: **다음 멤버의 크기**를 먼저 본다. `int`가 오면 4의 배수, `double`이 오면 8의 배수까지 채운다.

## 틀렸던 점 (기록)
| 처음 생각 | 실제 |
|---|---|
| A는 9바이트, B는 6바이트 (멤버 합) | 끝 패딩 때문에 A **12**, B **8** |
| C는 20바이트, D는 13바이트 | 가장 큰 정렬이 8이라서 C **24**, D **16** |
| 마지막 멤버 뒤에는 변수가 없으니 패딩이 없다 | **배열**의 다음 원소 정렬을 위해 끝 패딩이 들어간다 |
| 컴파일러가 큰 멤버 순으로 정렬한다 | 컴파일러는 **선언 순서를 유지**한다. 순서 변경은 프로그래머의 일 |
| 끝 패딩은 항상 4의 배수로 맞춘다 | **가장 큰 멤버의 정렬 단위**의 배수 (double이 있으면 8) |
| struct E는 20바이트 (char 뒤 패딩 3) | `double` 앞이라 패딩 **7** → **24바이트** |
| packed는 바이트 배치가 정해진 곳에 쓴다 (위험은 언급 안 함) | 정렬되지 않은 접근은 **느리거나 fault**가 날 수 있고, 멤버 포인터 사용이 위험하다 |

## 면접 대비 한 줄 요약
- "각 멤버는 자기 정렬 단위의 배수 offset에 선언 순서대로 놓이고, 구조체 크기는 가장 큰 멤버 정렬 단위의 배수로 맞춰집니다. 끝 패딩은 배열의 다음 원소도 정렬을 지키게 하려고 넣습니다. 큰 멤버부터 선언하면 패딩을 줄일 수 있고, packed는 통신 메시지처럼 배치가 고정된 곳에만 쓰되 정렬되지 않은 접근의 위험을 고려해야 합니다."
