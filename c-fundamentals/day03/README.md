# Day 03: 포인터 연산, 배열, 선언 읽기

## 목표
1. `p + 1`이 타입에 따라 몇 바이트 이동하는지 확인
2. 배열과 포인터의 관계 (`arr`, `&arr[0]`, `&arr`)
3. 배열을 함수에 넘기면 생기는 일 (포인터로 바뀜)
4. 복잡한 선언 읽기와 크기 확인
5. 바이트 단위 오프셋 계산 (메모리 플래너의 기본)

## 환경
- 보드: Jetson Xavier NX (ARM64, Ubuntu 20.04, gcc 9.4.0)
- 컴파일: `gcc -Wall -O0 -g array.c -o array`


## 기본 비유: 아파트
`int arr[4] = {10, 20, 30, 40};` = 방 4개짜리 1층
```
[1층]  101호  102호  103호  104호
        10     20     30     40
       (방 하나 = int 4바이트, 층 전체 = 16바이트)
```
- 방 하나의 크기 = 배열에 들어가는 타입의 크기 (`char`면 1바이트, `double`이면 8바이트)
- `int`가 4바이트인 것은 ARM64 리눅스 기준이다. C 표준은 `int` 크기를 정하지 않으므로, 임베디드에서는 `int32_t`, `uint8_t`처럼 크기가 이름에 적힌 타입을 많이 쓴다. (`char`만 항상 1바이트)

## 실험 1: 타입별 `p + 1`
| 타입 | 증가량 |
|---|---|
| `int*` | 4바이트 |
| `char*` | 1바이트 |
| `double*` | 8바이트 |

- 포인터 **자체의 크기**는 모두 8바이트(Day 02)지만, `p + 1`은 **가리키는 타입의 크기만큼** 이동한다.
- 덤: 스택에 `c`(...4b3), `i`(...4b4), `d`(...4b8)가 빈틈없이 배치됐다. `double`이 8의 배수 주소에 놓인 것은 정렬 규칙 때문이다. (Day 04)

## 실험 2: 배열과 포인터
- `arr`, `&arr[0]`, `&arr` 모두 주소 값이 같다 (`...4e8`).
- 하지만 `+1`의 결과가 다르다.
  - `arr + 1` → `...4ec` (**4바이트 뒤**, int 1개)
  - `&arr + 1` → `...4f8` (**16바이트 뒤**, 배열 전체)
- 이유: **주소 값은 같아도 타입이 다르다.**
  - `arr`은 식에서 첫 칸의 주소인 `int*`로 바뀐다. → 단위: 방 1개
  - `&arr`은 배열 포인터 `int (*)[4]`다. → 단위: 층 1개

### `2[arr]`이 컴파일되는 이유
- `a[b]`는 `*(a + b)`의 줄임말이다.
- `arr[2]` = `*(arr + 2)` = `*(2 + arr)` = `2[arr]` = 30
- 배열의 `[ ]`가 **포인터 덧셈으로 정의되어 있다**는 증거. 실제 코드에서는 쓰지 않는다.

## 실험 3: 배열을 함수에 넘기면
| 위치 | `sizeof(arr)` | 이유 |
|---|---|---|
| main 안 | 16 | 배열 전체 (int 4개 × 4바이트) |
| 함수 안 | 8 | 첫 칸의 주소가 담긴 **포인터** |

- 배열을 함수에 넘기면 배열 전체가 복사되지 않고 **첫 칸의 주소만** 넘어간다. `void f(int arr[])`는 `void f(int *arr)`와 같다.
- 배열 크기와 상관없이 8바이트다 (`int arr[1000]`이어도 8). 8이라는 숫자는 64비트 시스템이기 때문이다.
- 포인터에는 시작 주소만 있고 개수 정보가 없으므로, **길이를 따로 넘겨야 한다.**
  ```c
  void f(int *arr, size_t n);
  ```
- 함수 안에서 `sizeof(arr) / sizeof(arr[0])`을 쓰면 8 ÷ 4 = **2**가 나온다. 실제 개수(4)와 다르다.

## 실험 4: 선언 읽기와 크기
### 읽는 방법: 이름에서 출발해 안에서 밖으로
1. 변수 이름에서 시작
2. 오른쪽 먼저: `[ ]`가 있으면 "배열"
3. 오른쪽이 끝나거나 `)`를 만나면 왼쪽: `*`가 있으면 "포인터"
4. 괄호를 다 읽으면 괄호 밖으로 나가 반복
5. 마지막에 맨 왼쪽 타입을 붙임

`[ ]`가 `*`보다 우선순위가 높아서 오른쪽을 먼저 본다. `*`를 먼저 적용하고 싶을 때 괄호로 묶는다.

### 결과
| 선언 | 뜻 | 크기 |
|---|---|---|
| `int *a[4]` | int 포인터 **4개**가 든 배열 | 8 × 4 = **32** |
| `int (*b)[4]` | int 4개짜리 배열을 가리키는 포인터 **1개** | **8** |
| `int (*cc[3])[4]` | 배열 포인터 **3개**가 든 배열 | 8 × 3 = **24** |

- 포인터는 무엇을 가리키든 8바이트. **포인터가 몇 개인지**만 세면 된다.
- 배열 포인터(`int (*)[4]`)는 2차원 배열을 함수에 넘길 때 자주 쓰인다.

## 실험 5: 바이트 단위 오프셋 계산
```c
char buf[64];
int *t = (int*)(buf + 16);   // buf의 16바이트 뒤를 int로 사용
```
- `char*`는 `+1`이 1바이트라서 `buf + 16`은 **정확히 16바이트 뒤**다.
- `int*`였다면 `+16`은 16 × 4 = 64바이트 뒤가 된다.
- **메모리 플래너는 오프셋을 바이트 단위로 계산하고, 사용할 때 원하는 타입으로 변환한다.**
  ```c
  float *B = (float*)((char*)base + 100);   // 100바이트 위치
  // float *B = base + 100;                 // 잘못: 400바이트 위치
  ```
- 주의: 오프셋은 타입의 정렬에 맞아야 한다 (`int`, `float`은 4의 배수). GPU 버퍼는 보통 더 큰 단위로 정렬한다. (Day 04, 프로젝트 A 2주차에서 확인)

## 틀렸던 점 (기록)
| 처음 생각 | 실제 |
|---|---|
| `p + 1`은 포인터 크기인 8바이트씩 늘어난다 | **가리키는 타입의 크기**만큼 늘어난다 (int 4, char 1, double 8) |
| `arr + 1`과 `&arr + 1`은 32바이트, 8바이트 차이 | 4바이트(int 1개), **16바이트(배열 전체)** |
| `2[arr]`은 arr 값의 2배 | `*(2 + arr)` = `arr[2]` = **30** |
| `sizeof(arr)`는 main과 함수 안에서 같다 | main 16, 함수 안 **8** (포인터로 바뀜) |
| 선언 크기 해석을 못 함 | 포인터는 8바이트, **개수만 센다** (32, 8, 24) |
| char 버퍼에서 오프셋을 계산하는 이유를 몰랐음 | `char*`는 1칸 = 1바이트라서 **바이트 단위 계산**이 정확하다 |
| 함수 안 `sizeof(arr)/sizeof(arr[0])`은 1 (둘 다 8) | `arr[0]`은 int라서 4 → 8 ÷ 4 = **2** |

## 면접 대비 한 줄 요약
- "포인터 연산의 단위는 가리키는 타입의 크기입니다. 배열 이름은 식에서 첫 원소의 포인터로 바뀌고, 함수에 넘기면 포인터만 전달되어 길이 정보가 사라지므로 길이를 따로 넘겨야 합니다. 바이트 단위 오프셋은 char*로 계산한 뒤 필요한 타입으로 변환합니다."
