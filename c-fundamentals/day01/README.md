# Day 01: 프로세스 메모리 배치 (스택, 힙, 데이터, 코드)

## 목표
변수의 종류에 따라 메모리의 어느 영역에 놓이는지 확인한다.
1. 프로그램 **안에서** `printf`로 주소를 출력해 확인
2. 프로그램 **밖에서** `/proc/PID/maps`로 운영체제가 관리하는 메모리 배치를 확인
3. 두 결과가 일치하는지 비교

## 환경
- 보드: Jetson Xavier NX (ARM64, Ubuntu 20.04, L4T R35.6.4, glibc 2.31)
- 컴파일: `gcc -Wall -O0 -g memory.c -o memory`
- 개발: Cursor Remote-SSH로 Jetson에 직접 접속해 편집·실행

## 실험 대상
| 변수 | 종류 | 예상 영역 |
|---|---|---|
| `g_var` | 전역 변수 (초기값 1) | 데이터 (.data) |
| `s_var` | static 지역 변수 (초기값 2) | 데이터 (.data) |
| `g_zero` | 초기값 없는 전역 변수 | .bss |
| `g_zero2` | 0으로 초기화한 전역 변수 | .bss |
| `main_local` | main의 지역 변수 | 스택 |
| `other_local` | 다른 함수의 지역 변수 | 스택 |
| `heap` | `malloc` 할당 메모리 | 힙 |
| `main` | 함수 자체 | 코드 (.text) |

## 실험 1: 주소 출력과 ASLR

### ASLR 켠 상태 (2회 실행)
| 변수 | 1회차 | 2회차 |
|---|---|---|
| main_local | 0xffffcb47c0ec | 0xffffe9a3440c |
| other_local | 0xffffcb47c0c4 | 0xffffe9a343e4 |
| heap | 0xaaaac88922a0 | 0xaaab104ae2a0 |
| s_var | 0xaaaaab421014 | 0xaaaae3b61014 |
| g_var | 0xaaaaab421010 | 0xaaaae3b61010 |
| main 함수 | 0xaaaaab410930 | 0xaaaae3b50930 |

### ASLR 끈 상태 (`setarch -R`, 2회 실행, 두 번 모두 동일)
| 변수 | 주소 |
|---|---|
| main_local | 0xfffffffff33c |
| other_local | 0xfffffffff314 |
| heap | 0xaaaaaaab22a0 |
| s_var | 0xaaaaaaab1014 |
| g_var | 0xaaaaaaab1010 |
| main 함수 | 0xaaaaaaaa0930 |

### 분석
1. **주소 순서는 스택 > 힙 > 데이터 > 코드**로, 리눅스의 일반적인 메모리 배치와 일치한다.
2. **스택은 아래로 자란다.** `other_local`이 `main_local`보다 0x28(40바이트) 작다. `other_func`가 호출되면서 스택 프레임(지역 변수, 복귀 주소, 이전 프레임 포인터)만큼 스택이 아래로 늘어났다.
3. **ASLR**: 켜면 실행할 때마다 주소가 바뀌고, 끄면 매번 같다. 운영체제가 보안(주소 예측 방지)을 위해 배치를 무작위화한다는 직접 증거다.
4. **주소 끝 3자리(16진수)는 ASLR을 켜도 바뀌지 않는다.** (`main`은 항상 `...930`) ASLR이 페이지(4KB = 0x1000) 단위로 위치를 옮기기 때문에 페이지 안의 오프셋은 유지된다.
5. **코드와 데이터 사이 거리는 항상 같다.** (`g_var - main = 0x106e0`) 같은 실행 파일에 들어 있어 한 덩어리로 움직인다. 반면 힙 시작 위치(`brk`)는 별도로 무작위화되어 데이터와의 거리가 매번 달라진다.
6. **ASLR을 끄면 힙은 데이터 영역 바로 다음 페이지에서 시작한다.** `+0x2a0`은 malloc의 관리용 데이터 공간이다.
7. **`g_var`와 `s_var`는 4바이트 간격으로 붙어 있다.** 둘 다 초기화된 정적 수명 변수라서 같은 `.data` 섹션에 연속 배치된다. `static` 지역 변수는 이름이 보이는 범위(스코프)만 함수 안으로 제한될 뿐, 저장 위치와 수명은 전역 변수와 같다.
8. **0xaaaa...와 0xffff...는 ARM64 리눅스의 특징이다.** 사용자 공간으로 48비트 가상 주소를 쓰며, 스택은 공간의 맨 위, PIE 실행 파일은 `0xaaaa aaaa...` 근처에 올라간다. 출력된 주소는 모두 **가상 주소**이며, MMU가 실제 물리 주소로 변환한다.

## 실험 2: .data와 .bss

코드를 수정해 변수를 추가했기 때문에 코드 크기가 바뀌어 전체 주소가 이전 실험과 조금 다르다. (`setarch -R`)

| 변수 | 주소 | 섹션 |
|---|---|---|
| g_var | 0xaaaaaaab2010 | .data |
| s_var | 0xaaaaaaab2014 | .data |
| g_zero2 (`= 0`) | 0xaaaaaaab201c | .bss |
| g_zero (초기값 없음) | 0xaaaaaaab2020 | .bss |

### 분석
1. **`.bss`는 `.data`보다 높은 주소에 있다.** 배치 순서는 `코드 → .data → .bss → 힙`이다. (처음 예측은 "더 낮은 주소"였으나 틀림)
2. **`int g_zero;`와 `int g_zero2 = 0;`은 둘 다 `.bss`에 들어간다.**
3. **`.bss`를 따로 두는 이유**: 값이 전부 0인 변수는 실행 파일에 0을 실제로 저장할 필요가 없다. 필요한 크기만 기록해 두고, 실행할 때 운영체제가 0으로 채운 메모리를 만들어 준다. 예를 들어 `int big[1000000];`이 있어도 실행 파일 크기는 4MB 늘어나지 않는다.

## 실험 3: `/proc/PID/maps`로 메모리 배치 확인

### 방법
- `main`의 `free(heap);` 앞에 `getchar()`를 넣어 프로그램을 멈춤 (`#include <unistd.h>`, `getpid()`로 PID 출력)
- 다른 터미널에서 `cat /proc/$(pgrep -n memory)/maps` 실행
- 주의: `/proc/PID`는 프로세스가 실행 중일 때만 존재한다. (처음에 프로세스가 종료된 상태에서 실행해 `No such file or directory` 발생)

### 출력 (`setarch -R`)
```
aaaaaaaa0000-aaaaaaaa1000 r-xp 00000000 103:01 1084900   .../day01/memory
aaaaaaab1000-aaaaaaab2000 r--p 00001000 103:01 1084900   .../day01/memory
aaaaaaab2000-aaaaaaab3000 rw-p 00002000 103:01 1084900   .../day01/memory
aaaaaaab3000-aaaaaaad4000 rw-p 00000000 00:00 0          [heap]
fffff7e35000-fffff7f90000 r-xp 00000000 103:01 267687    .../libc-2.31.so
fffff7f90000-fffff7f9f000 ---p 0015b000 103:01 267687    .../libc-2.31.so
fffff7f9f000-fffff7fa3000 r--p 0015a000 103:01 267687    .../libc-2.31.so
fffff7fa3000-fffff7fa5000 rw-p 0015e000 103:01 267687    .../libc-2.31.so
fffff7fa5000-fffff7fa8000 rw-p 00000000 00:00 0
fffff7fcc000-fffff7fed000 r-xp 00000000 103:01 267584    .../ld-2.31.so
fffff7ff8000-fffff7ffa000 rw-p 00000000 00:00 0
fffff7ffa000-fffff7ffc000 r--p 00000000 00:00 0          [vvar]
fffff7ffc000-fffff7ffd000 r-xp 00000000 00:00 0          [vdso]
fffff7ffd000-fffff7ffe000 r--p 00021000 103:01 267584    .../ld-2.31.so
fffff7ffe000-fffff8000000 rw-p 00022000 103:01 267584    .../ld-2.31.so
fffffffdf000-1000000000000 rw-p 00000000 00:00 0         [stack]
```

### 한 줄 읽는 법
```
aaaaaaaa0000-aaaaaaaa1000  r-xp  00000000      103:01  1084900    .../memory
주소 범위                  권한  파일 안 위치  장치    파일 번호  연결된 파일
```
- 권한: `r` 읽기, `w` 쓰기, `x` 실행, `p` private(이 프로세스만의 복사본, 바꿔도 원본 파일은 그대로)

### printf 주소와 maps 비교 (모두 일치)
| 출력한 주소 | 들어가는 구역 | 권한 |
|---|---|---|
| `main` 0xaaaaaaaa09d0 | aaaaaaaa0000-aaaaaaaa1000 (memory) | `r-x` 코드 |
| `g_var`, `s_var`, `g_zero` 0xaaaaaaab20xx | aaaaaaab2000-aaaaaaab3000 (memory) | `rw-` .data + .bss |
| `heap` 0xaaaaaaab32a0 | aaaaaaab3000-aaaaaaad4000 | `[heap]` |
| `main_local` 0xfffffffff32c | fffffffdf000-1000000000000 | `[stack]` |

### 분석
1. **실행 파일 `memory`는 권한별로 3개 구역으로 나뉜다.**
   - `r-x`: 코드. 실행은 되지만 쓰기는 안 된다.
   - `r--`: 시작할 때 값을 채운 뒤 보안을 위해 쓰기를 막은 구역 (RELRO, 자세한 내용은 ELF 공부 때 확인)
   - `rw-`: `.data` + `.bss`. 읽기·쓰기는 되지만 실행은 안 된다.
2. **쓸 수 있는 곳은 실행할 수 없고, 실행할 수 있는 곳은 쓸 수 없다.** 데이터 영역에 악성 코드를 넣어도 실행되지 않게 막는 원리다.
3. **libc도 권한별로 여러 구역으로 나뉜다.** 라이브러리도 코드, 읽기 전용 데이터, 쓰기 가능한 데이터로 구성되는데, 메모리 권한은 **페이지(4KB) 단위**로만 설정할 수 있기 때문이다. `---p`는 정렬 때문에 생긴 접근 불가 빈틈이다.
4. **힙은 데이터 구역이 끝나는 `aaaaaaab3000`에서 바로 시작한다.**
5. **4바이트만 malloc했는데 힙은 0x21000(약 132KB)이다.** malloc은 비용이 큰 시스템 콜(`brk`)을 매번 부르지 않으려고 처음에 큰 덩어리를 받아 두고 그 안에서 나눠 준다. 프로젝트 A 2주차 메모리 플래닝(버퍼를 미리 잡아 두고 재사용)과 같은 아이디어다.
6. **힙과 스택 사이의 넓은 공간에 공유 라이브러리가 올라간다.**
   - `libc-2.31.so`: `printf`, `malloc` 등이 들어 있는 C 표준 라이브러리
   - `ld-2.31.so`: 프로그램 시작 시 libc를 찾아 메모리에 올리는 동적 링커
   - `[vdso]`, `[vvar]`: 커널이 넣어 준 코드와 데이터. `clock_gettime` 같은 자주 쓰는 기능을 커널 진입 없이 빠르게 처리한다. (프로젝트 A 벤치마크의 시간 측정도 이 경로를 사용)

## 실험 4: 코드 구역에 쓰기 (Segmentation fault)

```c
printf("main에 쓰기 시도\n");
*(int*)main = 0;        // 코드 구역에 쓰기
printf("여기는 출력될까?\n");
```
- 예측: 첫 번째 `printf`는 출력되고, 쓰기를 시도하는 순간 `Segmentation fault`로 종료되어 두 번째 `printf`는 출력되지 않는다.
- 이유: `main`은 `r-x` 권한의 코드 구역에 있어 쓰기 권한이 없다. 쓰기를 시도하면 MMU가 권한 위반을 감지하고, 커널이 SIGSEGV를 보내 프로세스를 종료한다.
- 실측: [ ] 실행 후 결과 기록

## 틀렸던 점 (기록)
| 처음 생각 | 실제 |
|---|---|
| `main`의 지역 변수는 코드 영역에 있다 | `main` **함수 자체**는 코드 영역, `main` **안의 지역 변수**는 스택에 있다 |
| 재실행 시 주소가 다른 이유: 이전 데이터가 메모리에 남아 있어서 | 프로세스가 끝나면 메모리는 모두 반납된다. 진짜 이유는 **ASLR** |
| 전역/static 변수가 붙어 있는 이유: 같은 "블럭"이라서 | 같은 **.data 섹션**에 링커가 순서대로 배치하기 때문 |
| 힙 위치가 바뀌는 이유: 무작위라서 | 힙 시작(`brk`)이 실행 파일과 **별도로** 무작위화되기 때문 |
| `.bss`는 `.data`보다 낮은 주소에 있다 | `.bss`는 `.data` **다음(높은 주소)**에 있다 |
| libc가 여러 구역으로 나뉜 이유: C 표준 라이브러리라서 | 권한이 다른 부분(코드/읽기 전용/쓰기 가능)이 있고, 권한은 **페이지 단위**로만 정할 수 있기 때문 |
| 힙이 132KB인 이유: 힙과 스택 사이 공간이 넓어서 | malloc이 시스템 콜을 줄이려고 **큰 덩어리를 미리 받아 두기** 때문 |
| main에 쓸 수 없는 근거: main_local에 rwx가 없어서 | `main`은 **코드 구역(r-x)**에 있어서 w가 없기 때문. 스택(main_local)은 실제로 `rw-` |

## 면접 대비 한 줄 요약
- "프로그램이 실행되면 운영체제는 코드, 데이터, bss, 힙, 공유 라이브러리, 스택을 가상 주소 공간에 배치하고, 각 구역에 페이지 단위로 권한을 줍니다. 코드는 r-x, 데이터는 rw-로 나눠서 쓰기와 실행을 동시에 허용하지 않습니다. 이 배치는 `/proc/PID/maps`로 직접 확인할 수 있습니다."
