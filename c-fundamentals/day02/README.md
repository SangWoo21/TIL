# Day 02: 포인터 기초

## 목표
주소를 담는 변수(포인터)의 동작을 직접 확인한다.
1. `&`, `*`, 포인터 값과 포인터 자체의 주소 구분
2. 포인터의 크기
3. 값 전달(call by value)과 주소 전달 비교 (swap)
4. 지역 변수의 주소를 반환하면 생기는 문제 (댕글링 포인터)

## 환경
- 보드: Jetson Xavier NX (ARM64, Ubuntu 20.04, gcc 9.4.0)
- 컴파일: `gcc -Wall -O0 -g pointer.c -o pointer`

## 핵심 개념
포인터는 **주소를 적어 둔 쪽지**다.

| 표현 | 뜻 |
|---|---|
| `&a` | a의 주소 |
| `p` | p에 들어 있는 값 (= a의 주소) |
| `*p` | p가 가리키는 곳의 값 (= a의 값) |
| `&p` | 쪽지 p 자체가 놓인 주소 |

## 실행 결과
```
a=10, &a=0xffffc6adc09c
p=0xffffc6adc09c, *p=10, &p=0xffffc6adc0a8
*p=20 이후 a=20
sizeof(int)=4, sizeof(int*)=8, sizeof(char*)=8, sizeof(double*)=8
swap_value 후: x=1, y=2
swap_pointer 후: x=2, y=1
마지막: &x=0xffffc6adc0a0, &y=0xffffc6adc0a4
q=(nil)
Segmentation fault (core dumped)
```

---

## 실험 1: 포인터의 기본
- `p`와 `&a`가 같다 (`0xffffc6adc09c`). p 안에 a의 주소가 들어 있다.
- `&p`(`0xffffc6adc0a8`)도 스택 주소다. p도 main의 지역 변수이기 때문이다.
- **a와 p는 둘 다 스택에 있고, p의 값이 a의 주소다.**
- `*p = 20`으로 a가 20이 됐다. 포인터로 원본을 바꿀 수 있다.

## 실험 2: 포인터의 크기
- `int*`, `char*`, `double*` 모두 **8바이트**다. ARM64는 주소가 64비트이기 때문이다.
- 가리키는 타입은 포인터 크기가 아니라 다음 두 가지를 결정한다.
  - `*p`로 읽을 때 **몇 바이트를 어떻게 해석할지**
  - `p + 1`을 할 때 **몇 바이트를 건너뛸지** (Day 03에서 확인)
- 32비트 시스템에서는 포인터가 4바이트다. → "포인터 크기는 시스템의 주소 크기에 따라 정해진다."

## 실험 3: swap_value와 swap_pointer
- `swap_value(x, y)`: 값이 바뀌지 않는다. 함수가 자기 스택 프레임에 만든 **복사본**만 바꾸기 때문이다.
- `swap_pointer(&x, &y)`: 값이 바뀐다. **주소**를 받아서 그 주소의 원본 값을 바꾸기 때문이다.
- **주소는 바뀌지 않는다.** 변수의 주소는 변수가 살아 있는 동안 변하지 않는다. swap_pointer는 사물함 위치가 아니라 **두 사물함의 내용물을 맞바꾼다.**
- [ ] `처음:` 줄(`&x`, `&y` 출력)을 추가해 `마지막:` 줄과 주소가 같은지 실측 확인

## 실험 4: 지역 변수의 주소 반환 (댕글링 포인터)
```c
int *bad_func(void) {
    int local = 42;
    return &local;
}
```
- 예측: 42가 나온다 → **실제: `q=(nil)`, Segmentation fault**
- **개념**: bad_func가 끝나면 스택 프레임이 사라지므로 `local`의 주소는 유효하지 않다. 이런 포인터를 **댕글링 포인터**라고 한다.
- **실제로 일어난 일**: gcc가 이 실수를 감지하고, 주소 대신 **NULL(0)을 반환하도록** 코드를 생성했다. 그 NULL을 읽으려다 프로그램이 죽었다.
- 컴파일러나 최적화 옵션에 따라 42, 쓰레기 값, 크래시 중 무엇이든 나올 수 있다. 이런 상황을 **정의되지 않은 동작(Undefined Behavior)**이라고 한다. "운 좋게 42가 나왔으니 괜찮다"가 가장 위험하다.
- [ ] 컴파일 경고 메시지 기록 (`warning: function returns address of local variable` 예상)

### 안전하게 42를 돌려주는 방법
| 방법 | 단점 |
|---|---|
| 값 자체를 반환 (`int func(void) { return 42; }`) | 없음. 주소가 필요 없으면 가장 안전 |
| `static int local = 42;` (데이터 영역) | 모든 호출이 같은 변수를 공유. 멀티스레드에서 값이 꼬일 수 있음 |
| `malloc` (힙 영역) | 호출한 쪽에서 반드시 `free`해야 함. 잊으면 메모리 누수 |

### NULL을 읽으면 왜 Segmentation fault가 나는가
- NULL은 0번 주소다.
- Day 01의 maps에서 가장 낮은 구역은 `aaaaaaaa0000`부터 시작했다. **0번 주소는 어떤 구역에도 매핑되어 있지 않다.**
- CPU가 0번 주소에 접근하면 MMU에서 페이지 폴트가 나고, 커널이 SIGSEGV를 보내 프로세스를 종료한다.
- 리눅스는 0번 근처 주소를 일부러 매핑하지 못하게 막아 둔다. 그래서 NULL 실수는 조용히 넘어가지 않고 **항상 바로 드러난다.**

## 틀렸던 점 (기록)
| 처음 생각 | 실제 |
|---|---|
| 포인터 크기는 타입마다 다르다 (4, 10, 8) | 모든 포인터는 **8바이트**(ARM64). 타입은 읽는 방법과 `p+1`의 이동 크기를 정한다 |
| swap_pointer는 x, y의 주소 자체를 바꾼다 | 주소는 그대로이고, **그 주소에 있는 값**을 맞바꾼다 |
| 지역 변수의 주소를 반환해도 42가 나온다 | 스택 프레임이 사라져 **댕글링 포인터**가 된다. 이번에는 gcc가 NULL을 반환해 크래시 |
| NULL을 읽으면 왜 죽는지 몰랐음 | 0번 주소는 매핑되지 않아 MMU 페이지 폴트 → SIGSEGV |

## 면접 대비 한 줄 요약
- "C는 인자를 값으로 전달하므로 함수 안에서 원본을 바꾸려면 주소를 넘겨야 합니다. 반대로 지역 변수의 주소를 함수 밖으로 돌려주면, 함수가 끝나면서 스택 프레임이 사라져 댕글링 포인터가 됩니다. 이는 정의되지 않은 동작이라 결과를 믿을 수 없습니다."
